# V8.5.20 변경 사항

## 1. CCTV 화면이 실제로 들어와도 `CCTV 연결 중`에 가려지던 문제 수정

V8.5.19의 CCTV 창은 무한 MJPEG 응답에 대해 브라우저의 `img.onload` 이벤트가 발생하기를 기대했습니다. Chrome/Chromium에서는 MJPEG가 계속 열린 상태라 `onload`가 늦거나 발생하지 않을 수 있고, 그 결과 실제 JPEG가 `<img>`에 들어와 있어도 전체 화면 `CCTV 연결 중` 레이어가 그대로 남을 수 있었습니다.

V8.5.20은 `naturalWidth`/`naturalHeight`를 100ms 간격으로 확인합니다. 첫 JPEG가 디코딩되는 순간 로딩 레이어를 제거해 실제 영상 또는 백엔드 재연결 상태 JPEG를 바로 보여줍니다.

## 2. raw 영상과 AI 영상을 두 레이어로 분리

기존에는 CCTV 창 포커스가 바뀔 때 같은 `<img>`의 URL을 `/api/stream-raw`와 `/api/stream-annotated` 사이에서 교체했습니다. 이때 브라우저 MJPEG 연결이 매번 다시 시작되어 검은 화면 또는 `연결 중` 공백이 생길 수 있었습니다.

V8.5.20은 raw 영상을 창이 열려 있는 동안 계속 유지합니다. 포커스된 창에서는 AI 스트림을 별도 레이어로 시작하고 첫 AI 프레임이 준비된 이후에만 위에 표시합니다. 따라서 AI 연결이 늦더라도 raw CCTV 영상은 계속 보입니다.

## 3. HLS 세그먼트 전환 지연 감소

- master playlist에서 확인한 media playlist URL을 재사용합니다.
- 첫 연결은 가장 최신 세그먼트가 아직 쓰이는 중일 가능성을 고려해 가능한 경우 한 조각 이전의 안정된 세그먼트부터 시작합니다.
- 이미 본 세그먼트보다 새 세그먼트만 선택합니다.
- 정상 HLS fallback이 한 번 성공하면 그 경로를 유지합니다.
- V8.5.19에서 30초마다 OpenCV 직접 연결을 다시 시도하며 생길 수 있던 1~2초 영상 멈춤을 제거했습니다.

## 4. CCTV HTTP 연결 분리

CCTV capture thread마다 별도의 `requests.Session` 연결 풀을 사용하도록 변경했습니다. 여러 CCTV가 동시에 열렸을 때 한 카메라의 느린 HLS 요청이 다른 카메라 요청과 세션 상태를 공유하지 않도록 했습니다.

또한 일반 CCTV 미디어 요청에 `Origin` 헤더를 강제로 붙이지 않습니다. 카메라 제공 서버가 cross-origin Origin 헤더를 거부하는 경우에는 접근 성공률이 올라갑니다. UTIS CCTV 목록 API 호출에는 기존 Origin/Referer 헤더를 그대로 사용합니다.

## 5. 확인 결과

- 전체 pytest: 44개 통과
- 번들 테스트 CCTV raw MJPEG: 서버 요청 후 첫 JPEG chunk 약 12ms, 실제 동영상 프레임 약 170ms부터 확인
- 약 0.69초 동안 수집한 8개 JPEG가 모두 서로 다른 프레임으로 확인되어 영상 진행을 검증함

외부 포항 CCTV 서버는 이 작업 환경에서 DNS/인터넷 접속이 차단되어 실제 원격 카메라 끝단까지는 검증하지 못했습니다.
