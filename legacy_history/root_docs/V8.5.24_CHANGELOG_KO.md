# V8.5.24 변경 내역

## 이번에 원인을 다시 잡은 이유

V8.5.23의 핵심 문제가 단순 HLS 재연결 시간이 아니었습니다. 각 CCTV 창이 `raw JPEG`와 `AI JPEG`를 독립적인 HTTP `fetch()` 요청으로 반복해서 받도록 바뀌면서, 여러 창을 열면 한 브라우저에서 같은 `127.0.0.1:8000` 서버로 매우 많은 짧은 요청이 동시에 발생했습니다. 실제 녹화에서 여러 창이 한꺼번에 `응답 시간 초과 (3초)`로 바뀐 것이 이 구조와 일치했습니다. 이전 수정은 이 요청을 더 빨리 재시도하는 방향이어서 증상을 충분히 없애지 못했습니다.

V8.5.24는 CCTV 영상 전달 방식을 다시 설계했습니다.

## 1. CCTV 영상 전송: 여러 HTTP 폴링 -> WebSocket 1개

- 브라우저는 CCTV 창 수와 관계없이 `/ws/cctv` WebSocket **한 개**만 사용합니다.
- 열린 카메라 목록과 현재 선택 카메라를 한 번의 subscribe 메시지로 서버에 보냅니다.
- 서버는 모든 CCTV의 최신 JPEG를 같은 WebSocket으로 멀티플렉싱합니다.
- 선택 창은 약 10fps, 정렬된 다른 창은 약 5fps를 목표로 전송합니다.
- 브라우저 JPEG 디코딩이 늦으면 오래된 프레임을 큐에 쌓지 않고 **항상 가장 최신 프레임만** 남깁니다. 그래서 몇 초 뒤의 옛 영상이 뒤늦게 재생되는 backlog를 만들지 않습니다.
- 화면은 `<canvas>`에 그리며, 전송이 잠깐 재연결되어도 마지막 정상 프레임을 지우지 않습니다.
- 기존 `/api/cctv/frame-raw`, `/api/cctv/frame-annotated`, MJPEG API는 호환성 목적으로 남겼지만 기본 화면 전송에는 사용하지 않습니다.

## 2. 장시간 켜 두었을 때 화면이 사라지는 문제

- 긴 `<img src="multipart MJPEG">` 연결과 카메라마다 반복되는 Blob URL 교체를 기본 영상 경로에서 제거했습니다.
- 하나의 WebSocket에 1초 watchdog을 두고, 채널이 끊기거나 5.5초 이상 아무 메시지도 없으면 자동으로 다시 연결합니다.
- 재연결 상태 JPEG는 이미 정상 CCTV를 한 번 표시한 canvas를 덮지 않습니다. 네트워크가 잠깐 끊겨도 마지막 정상 화면이 남습니다.
- 서버 worker의 capture/render 핵심 스레드가 실제로 종료된 경우 기존 worker를 계속 재사용하지 않고 새 worker를 생성합니다.

## 3. 영상 렉 감소

- 브라우저가 JPEG 한 장을 디코딩하는 동안 더 최신 프레임이 도착하면 이전 프레임은 그리지 않고 최신 프레임으로 건너뜁니다.
- AI 렌더가 0.85초 이상 오래되면 WebSocket은 일시적으로 최신 raw 프레임으로 전환해 영상 자체가 멈추지 않게 합니다.
- raw 복구 출력은 약 8fps까지 낼 수 있도록 했고 AI 렌더가 다시 정상화되면 자동으로 annotated 영상으로 돌아옵니다.
- 카메라마다 raw+AI HTTP 요청을 동시에 수행하지 않으므로 다중 창에서 브라우저 요청 대기열이 쌓이지 않습니다.

## 4. 박스가 한 프레임 건너 사라지는 실제 버그 수정

V8.5.23의 저신뢰 박스 확인 코드에는 상태 버그가 있었습니다. 2회 연속 확인되어 화면에 표시된 약한 후보를 `pending` 상태에서 제거해 버렸기 때문에 다음 AI 주기에는 확인 횟수가 다시 1부터 시작했습니다. 결과적으로 동일 차량 박스가 `표시 -> 사라짐 -> 표시`처럼 깜빡일 수 있었습니다.

V8.5.24에서는 확인된 약한 후보도 temporal state에 계속 유지하여 다음 검출에서 2/3회 확인 상태가 이어지게 했습니다.

## 5. 이상한 박스 억제

- 전체 화면 검출은 0.42 이상이면 즉시 표시하고 그보다 약한 박스는 연속 확인을 요구합니다.
- 타일 rescue 박스는 오검출 위험이 높아 0.55 이상만 즉시 표시하고 약한 타일 박스는 3회 확인합니다.
- 타일 내부 절단 경계에 걸린 0.50 미만 조각 박스를 제거합니다.
- 차량 기본 confidence는 0.28, rescue confidence는 0.26으로 조정했습니다.
- 지나치게 세로/가로로 찌그러진 박스 및 화면의 48%를 넘는 비정상 박스를 제거합니다.
- Optical Flow가 약한 박스를 도로선/표지판 쪽으로 끌고 가는 것을 줄이기 위해 저신뢰 박스의 inlier 조건을 강화하고 한 프레임 최대 이동량을 제한했습니다.
- flow 실패 시 이전 속도로 계속 밀어내는 비율을 크게 줄여 오래된 박스가 엉뚱한 위치로 흘러가지 않게 했습니다.

## 6. 실행 방식

사용자가 정상 동작을 확인한 VS Code PowerShell 방식인 `python -m app.main`을 기본 실행 방법으로 문서화했습니다. 자세한 내용은 `RUN_V8.5.24_KO.md`를 확인하십시오.

## 7. 검증

- Python 핵심 파일 컴파일 검사 통과
- `node --check app/static/app.js` 통과
- 자동 회귀 테스트 72개 통과
- WebSocket binary packet의 header/JPEG 분리 프로토콜을 가짜 CCTV packet으로 직접 호출해 검증
- 번들 `flood-test-01.mp4`에서 모델 추론을 stub으로 분리한 영상 전송 검사: 5초 동안 50회 샘플 중 43개의 서로 다른 frame sequence, 49회 실제 영상 packet 수신. 즉 새 전송 계층 자체가 한 프레임에 멈추지 않고 지속 갱신되는 것을 확인

실제 포항 외부 CCTV 원본 서버의 순간적인 장애/지연까지 로컬 테스트에서 재현할 수는 없지만, 이번 버전은 브라우저 쪽 다중 HTTP 요청 병목과 박스 temporal-state 버그를 코드 구조에서 직접 제거했습니다.
